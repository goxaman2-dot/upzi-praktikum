# CLAUDE.md — заметки по проекту «Практикум УПЗИ и ЭЗИ»

Этот файл — персистентный контекст для Claude между сессиями (не для студентов и не для читателей README.md). Сюда заносятся архитектурные решения, открытые вопросы и договорённости с преподавателем, которые не видны напрямую из кода `index.html`.

## О проекте

Одностраничное веб-приложение (`index.html`, без сборки) — интерактивный практикум по управлению проектами информационной безопасности. Три портфеля проектов (ИТСО, программно-аппаратный, организационно-административный), Старт 0 (подбор персонала/ресурсов фирмы) + 9 занятий на каждый из 3 проектов. Печатный отчёт формируется в браузере через JSZip/OMML напрямую в JS (без docx-скилла). Деплой — GitHub Pages: https://goxaman2-dot.github.io/upzi-praktikum/

## Открытые архитектурные вопросы

### Хранение и подлинность данных студентов (обсуждение от 2026-07-26)

**Проблема.** Сейчас прогресс студента хранится только в JSON-файле, который он сам экспортирует/импортирует (кнопки 💾/📂, флешка или локальный диск аудиторского компьютера). Риски:
- потеря/забывание сохранить, потерянные флешки, путаница файлов между студентами;
- умышленное удаление файла, чтобы скрыть плохой результат теста на компетенции и начать заново;
- многократное использование кнопки «Пройти тест заново» до случайного попадания на правильные ответы;
- секретное сочетание клавиш (0-0-0-2-5 / 0-0-0-4-0 для занятия 8) и сам массив правильных ответов `COMPETENCY_TESTS` лежат в открытом клиентском JS — любой студент через «Просмотр кода» браузера видит их за секунды. Это НЕ секретность в смысле защиты, а отсутствие кнопки в интерфейсе.

**Предложенное направление (Google Таблицы/Диск как хранилище).** Обсуждали использование Google Sheets/Drive: у каждого студента — личная папка/строка, видимая только ему и преподавателю (права доступа по email, не «по ссылке»).

Что это РЕШАЕТ:
- подмену/чтение чужих данных другим студентом (авторизация на стороне Google, а не в клиентском JS);
- потерю файлов/флешек — данные централизованы;
- бесплатную историю версий (Google Таблицы/Диск логируют изменения с таймстампами — подделать «сдал вовремя» задним числом сложнее, чем отредактировать локальный JSON).

Что это НЕ решает без дополнительного шага:
- манипуляцию студентом СВОИМИ результатами — потому что подсчёт результата теста по-прежнему происходит в браузере студента, который видит исходный код целиком. Студент может либо прочитать правильные ответы через «Просмотр кода», либо — тоньше — перехватить сетевой запрос сохранения результата и отправить туда руками сфабрикованный результат, вообще не проходя тест в интерфейсе;
- совместное использование аккаунта/прохождение теста другом — социальная проблема, не техническая;
- бесконтрольные повторные попытки — если ограничение количества попыток остаётся только на клиенте.

**Вывод.** Чтобы по-настоящему закрыть манипуляцию результатом (а не только хранилище), проверку ответов нужно перенести на сторону сервера (например, Google Apps Script как лёгкий бэкенд): студент отправляет туда сырые ответы (какой вариант отметил на каждый вопрос), а сверка с ключом правильных ответов происходит НА СЕРВЕРЕ, где клиент этот ключ никогда не видит. Это уже не смена хранилища, а разнесение приложения на клиент + сервер — заметно больший объём работы (OAuth, отдельный Google Cloud проект/Apps Script, тестирование под разными аккаунтами), чем правка в существующем файле.

Статус: обсуждение, реализация не начата. Если преподаватель решит двигаться в эту сторону — начинать с переноса именно логики проверки (не только хранения) на сервер, иначе решение даст ложное чувство защищённости.

**Известный баг docx.js (v9.7.1) с `ImportedXmlComponent.fromXmlString()` — важно при повторной сборке Главы 6 или любой новой главы через docx.js.** Первая собранная версия Главы 6 открывалась LibreOffice/`soffice --headless` без единой жалобы (и визуально рендерилась идеально — все 6 формул), но реальный Word на компьютере преподавателя отказывался открывать файл («Ошибка Word при попытке открытия файла... Откройте файл с помощью конвертера резервных копий»). Причина: `ImportedXmlComponent.fromXmlString(xml)` парсит переданную строку в режиме «целый XML-документ» через `xml2js(..., {compact:false})`, и верхний узел этого разбора (сам `#document`, не переданный элемент `<m:oMath>`) не имеет свойства `.name` — конструктор `new ImportedXmlComponent(element.name, ...)` получает `rootKey = undefined` и сериализует НАСТОЯЩИЙ `<m:oMath>...</m:oMath>` obёрнутым в буквальный, ничего не значащий тег `<undefined>...</undefined>`. LibreOffice такой мусорный тег молча игнорирует при рендеринге; Word проверяет документ на соответствие OOXML-схеме куда строже и отказывается открывать файл целиком, а не только конкретную формулу. Обнаружено это ТОЛЬКО после того, как преподаватель попытался открыть файл в реальном Word — рендер-проверка через `soffice`/`pdftoppm`, рекомендованная SKILL.md докс-скилла, эту категорию ошибок не ловит. **Исправление** (уже внесено в `build_glava6.js`, см. функцию `Formula()`): после `const wrapper = ImportedXmlComponent.fromXmlString(xml)` нужно брать не сам `wrapper`, а его первый дочерний элемент — `const math = wrapper.root[0]` — именно он и есть настоящий `<m:oMath>`-компонент без мусорной обёртки. Проверять результат надо не только рендер-скриншотом, но и XSD-валидатором скилла: `python3 <скилл>/scripts/office/validate.py -v файл.docx` — баг проявляется как `Element 'undefined': This element is not expected.` в `word/document.xml`. Главы 1-5 этой проблемой не затронуты (собраны раньше, другим способом/версией).

**Ещё один нюанс OMML, обнаруженный при сборке Главы 7**: помимо уже описанного бага `<undefined>`-обёртки, есть вторая ловушка в существующей helper-функции `frac(num, den)` из `build_glava6.js` — она подставляет `num`/`den` ВНУТРЬ `<m:t>` (текстовый узел), что верно только если `num`/`den` — обычный текст. Если числитель/знаменатель сам является OMML-элементом (например, результат `sSub()` для `Hₑ/Tₑ`), нельзя вкладывать один `<m:sSub>` внутрь `<m:t>` — эта вложенность нарушает XSD (`m:t` — простой текстовый тип, дочерние элементы в нём запрещены) и ловится тем же `validate.py` с ошибкой `Element '{...}t': Element content is not allowed`. Для дробей с OMML-содержимым числителя/знаменателя использован отдельный `fracRaw(numOmml, denOmml)`, который вставляет содержимое `<m:num>`/`<m:den>` без обёртки в `<m:t>`. Правило на будущее: `frac()` — только для дробей из простого текста; как только числитель/знаменатель сам является результатом `sSub()`/`sSup()`/другого OMML-хелпера — нужен `fracRaw()`.

Правило на будущее: для донат-диаграмм в SVG-макетах этого проекта использовать ТОЛЬКО path-based дуги, не `stroke-dasharray+rotate` на `<circle>`.
