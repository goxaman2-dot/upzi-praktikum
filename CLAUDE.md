# CLAUDE.md — заметки по проекту «Практикум УПЗИ и ЭЗИ»

Этот файл — персистентный контекст для Claude между сессиями (не для студентов и не для читателей README.md). Сюда заносятся архитектурные решения, открытые вопросы и договорённости с преподавателем, которые не видны напрямую из кода `index.html`.

## О проекте

Одностраничное веб-приложение (`index.html`, без сборки) — интерактивный практикум по управлению проектами информационной безопасности. Три портфеля проектов (ИТСО, программно-аппаратный, организационно-административный), Старт 0 (подбор персонала/ресурсов фирмы) + 9 занятий на каждый из 3 проектов. Печатный отчёт формируется в браузере через JSZip/OMML напрямую в JS (без docx-скилла). Деплой — GitHub Pages: https://goxaman2-dot.github.io/upzi-praktikum/

## Открытые архитектурные вопросы

### Хранение и подлинность данных студентов (обсуждение от 2026-07-26)

**Проблема.** Сейчас прогресс студента хранится только в JSON-файле, который он сам экспортирует/импортирует (кнопки 💾/📂, флешка или локальный диск аудиторского компьютера). Риски:
- потеря/забывание сохранить, потерянные флешки, путаница файлов между студентами;
- умышленное удаление файла, чтобы скрыть плохой результат теста на компетенции и начать заново;
- многократное использование кнопки «Пройти тест заново» до случайного попадания на правильные ответы;
- секретное сочетание клавиш (0-0-0-2-5 / 0-0-0-4-0 для занятия 8) и сам массив правильных ответов `COMPETENCY_TESTS` лежат в открытом клиентском JS — любой студент через «Просмотр кода» браузера видит их за секунды. Это НЕ секретность в смысле защиты, а отсутствие кнопки в интерфейсе.

**Предложенное направление (Google Таблицы/Диск как хранилище).** Обсуждали использование Google Sheets/Drive: у каждого студента — личная папка/строка, видимая только ему и преподавателю (права доступа по email, не «по ссылке»).

Что это РЕШАЕТ:
- подмену/чтение чужих данных другим студентом (авторизация на стороне Google, а не в клиентском JS);
- потерю файлов/флешек — данные централизованы;
- бесплатную историю версий (Google Таблицы/Диск логируют изменения с таймстампами — подделать «сдал вовремя» задним числом сложнее, чем отредактировать локальный JSON).

Что это НЕ решает без дополнительного шага:
- манипуляцию студентом СВОИМИ результатами — потому что подсчёт результата теста по-прежнему происходит в браузере студента, который видит исходный код целиком. Студент может либо прочитать правильные ответы через «Просмотр кода», либо — тоньше — перехватить сетевой запрос сохранения результата и отправить туда руками сфабрикованный результат, вообще не проходя тест в интерфейсе;
- совместное использование аккаунта/прохождение теста другом — социальная проблема, не техническая;
- бесконтрольные повторные попытки — если ограничение количества попыток остаётся только на клиенте.

**Вывод.** Чтобы по-настоящему закрыть манипуляцию результатом (а не только хранилище), проверку ответов нужно перенести на сторону сервера (например, Google Apps Script как лёгкий бэкенд): студент отправляет туда сырые ответы (какой вариант отметил на каждый вопрос), а сверка с ключом правильных ответов происходит НА СЕРВЕРЕ, где клиент этот ключ никогда не видит. Это уже не смена хранилища, а разнесение приложения на клиент + сервер — заметно больший объём работы (OAuth, отдельный Google Cloud проект/Apps Script, тестирование под разными аккаунтами), чем правка в существующем файле.

Статус: обсуждение, реализация не начата. Если преподаватель решит двигаться в эту сторону — начинать с переноса именно логики проверки (не только хранения) на сервер, иначе решение даст ложное чувство защищённости.

**Известный баг docx.js (v9.7.1) с `ImportedXmlComponent.fromXmlString()` — важно при повторной сборке Главы 6 или любой новой главы через docx.js.** Первая собранная версия Главы 6 открывалась LibreOffice/`soffice --headless` без единой жалобы (и визуально рендерилась идеально — все 6 формул), но реальный Word на компьютере преподавателя отказывался открывать файл («Ошибка Word при попытке открытия файла... Откройте файл с помощью конвертера резервных копий»). Причина: `ImportedXmlComponent.fromXmlString(xml)` парсит переданную строку в режиме «целый XML-документ» через `xml2js(..., {compact:false})`, и верхний узел этого разбора (сам `#document`, не переданный элемент `<m:oMath>`) не имеет свойства `.name` — конструктор `new ImportedXmlComponent(element.name, ...)` получает `rootKey = undefined` и сериализует НАСТОЯЩИЙ `<m:oMath>...</m:oMath>` obёрнутым в буквальный, ничего не значащий тег `<undefined>...</undefined>`. LibreOffice такой мусорный тег молча игнорирует при рендеринге; Word проверяет документ на соответствие OOXML-схеме куда строже и отказывается открывать файл целиком, а не только конкретную формулу. Обнаружено это ТОЛЬКО после того, как преподаватель попытался открыть файл в реальном Word — рендер-проверка через `soffice`/`pdftoppm`, рекомендованная SKILL.md докс-скилла, эту категорию ошибок не ловит. **Исправление** (уже внесено в `build_glava6.js`, см. функцию `Formula()`): после `const wrapper = ImportedXmlComponent.fromXmlString(xml)` нужно брать не сам `wrapper`, а его первый дочерний элемент — `const math = wrapper.root[0]` — именно он и есть настоящий `<m:oMath>`-компонент без мусорной обёртки. Проверять результат надо не только рендер-скриншотом, но и XSD-валидатором скилла: `python3 <скилл>/scripts/office/validate.py -v файл.docx` — баг проявляется как `Element 'undefined': This element is not expected.` в `word/document.xml`. Главы 1-5 этой проблемой не затронуты (собраны раньше, другим способом/версией).

**Ещё один нюанс OMML, обнаруженный при сборке Главы 7**: помимо уже описанного бага `<undefined>`-обёртки, есть вторая ловушка в существующей helper-функции `frac(num, den)` из `build_glava6.js` — она подставляет `num`/`den` ВНУТРЬ `<m:t>` (текстовый узел), что верно только если `num`/`den` — обычный текст. Если числитель/знаменатель сам является OMML-элементом (например, результат `sSub()` для `Hₑ/Tₑ`), нельзя вкладывать один `<m:sSub>` внутрь `<m:t>` — эта вложенность нарушает XSD (`m:t` — простой текстовый тип, дочерние элементы в нём запрещены) и ловится тем же `validate.py` с ошибкой `Element '{...}t': Element content is not allowed`. Для дробей с OMML-содержимым числителя/знаменателя использован отдельный `fracRaw(numOmml, denOmml)`, который вставляет содержимое `<m:num>`/`<m:den>` без обёртки в `<m:t>`. Правило на будущее: `frac()` — только для дробей из простого текста; как только числитель/знаменатель сам является результатом `sSub()`/`sSup()`/другого OMML-хелпера — нужен `fracRaw()`.

**Технический метод**: прямая склейка `word/document.xml` 20 исходных файлов (Python, без `docx-js` и без пересборки контента с нуля) — из каждого файла вырезано содержимое `<w:body>` (от начала до последнего `<w:sectPr>`, который отбрасывается для всех файлов, кроме первого — единственный `<w:sectPr>` итогового документа взят из Главы 1 и перенесён в самый конец собранного тела, т.к. все 20 источников используют идентичные параметры страницы). Между блоками вставлен ручной разрыв страницы (`<w:br w:type="page"/>` в отдельном параграфе) — не программная секция, т.к. секция не нужна при полностью одинаковой геометрии страницы у всех источников. Проверка боковых рисков перед сборкой (см. выше) показала: закладок (`w:bookmarkStart`) — 0 во всех 20 файлах (в отличие от бланков Роспатента, где коллизия ID закладок была реальной проблемой, здесь этот риск попросту отсутствовал), поэтому оффсеты закладок не потребовались.

**Обработка изображений** — единственная содержательная сложность склейки: в 20 исходниках суммарно 53 картинки (SVG-рендеры учебника + скриншоты/SVG-макеты путеводителя), и относительные ID связей (`rId7`, `rId8`...) у каждого файла назначены независимо и массово повторяются между файлами. Решение: для каждого исходного файла — вычитать его `word/_rels/document.xml.rels`, найти все связи типа `image`, скопировать соответствующий файл `word/media/*` в объединённую медиатеку под новым уникальным именем (`f{индекс_файла:02d}_{исходное_имя}`, чтобы визуально было видно происхождение при отладке), назначить новый глобальный `rId` (сквозной счётчик, начиная с `rId5000`, — с большим запасом от стандартных 7 служебных связей каждого исходника: styles/numbering/footnotes/endnotes/settings/comments/fontTable) и переписать все вхождения `r:embed="rIdN"` в тексте этого файла на новый ID регулярным выражением ДО того, как его тело добавляется в общий список. Базовые служебные файлы (`styles.xml`, `numbering.xml`, `footnotes.xml`, `endnotes.xml`, `settings.xml`, `fontTable.xml`, `comments.xml`, `[Content_Types].xml`, `docProps/*`) взяты целиком из первого исходника (Введение+Глава1) без изменений — обосновано отсутствием именованных стилей/списков/комментариев в остальных 19 файлах.

**Найденный и исправленный баг сборки**: первая версия `validate.py` вернула 4 ошибки «Unreferenced file» (`docProps/app.xml`, `docProps/core.xml`, `docProps/custom.xml`, `word/document.xml`) — причина в том, что я скопировал `word/_rels/document.xml.rels`, но забыл корневой пакетный файл `_rels/.rels` (тот, что живёт в корне ZIP-архива и объявляет сам факт существования `word/document.xml`/`docProps/*` как частей пакета верхнего уровня, отдельно от `word/_rels/document.xml.rels`, который описывает связи ВНУТРИ `word/document.xml`). Исправлено копированием `_rels/.rels` из первого исходника — файл, который легко упустить, т.к. он лежит вне папки `word/` и не встречался в этом проекте раньше (все более ранние правки этой сессии редактировали уже существующие файлы, где этот корневой rels никогда не трогался).

**Верификация**: `validate.py` — 0 ошибок; рендер в PDF (196 страниц) проверен выборочно постранично в ключевых точках — титульная страница, переход Глава3→Часть3 (граница страниц 78/79, разрыв ровный, без наползаний), таблица 26 и рисунок 11 Главы 7 внутри сводного тома (перенеслись корректно, шапка таблицы повторяется на второй странице благодаря `cantSplit`, добавленному ещё на этапе правки самой Главы 7), скриншот с 9 картинками страницы Путеводителя Старт0+1 (картинка на месте, не потеряна при массовом ремаппинге rId), и последняя страница документа (путеводитель по итоговому отчёту, обрыва текста нет). Числа страниц по разделам, предъявленные преподавателю до сборки (Путеводитель — 61 стр. по 10 частям, Учебник — 129 стр. по 10 главам без учёта дополнения Главы 7), после дописывания Главы 7 (+4 стр.: 6→10) и добавления титульного листа и принудительных разрывов страниц между 20 блоками (несколько «пустых хвостов» на конце страницы перед принудительным разрывом) выросли до итоговых 196 — расхождение с постраничной арифметикой объяснимо и ожидаемо, не является дефектом.

## Встраивание комплекта документов в живой практикум — 06.08.2026 (позже в тот же день)

По прямой просьбе преподавателя («как ВСТРОИТЬ эти 14 и 6 перечней документов в практикум!? как ты видишь?», затем уточнение «по 5 на 20-ть проектов» — единый каркас на все 20 типов, а не два раздельных списка) реализована живая, вычисляемая функция `canonicalDocSet(projectType)` (index.html, сразу после `GANTT_SOFT_SPECIFIC`) — не хардкод повторяющий уже собранный DOCX, а единый источник правды: для портфеля I (ИТСО, 6 типов) берётся напрямую из `GANTT_ITSO` (строки этапа V — одинаковые 5 документов у всех шести типов, т.к. их `apply` совпадают); для портфелей II/III (14 типов) — специфический документ типа из `GANTT_SOFT_SPECIFIC` + строки `GANTT_SOFT_COMMON` этапов IV/V с `apply[projectType]===true`. **Ключевое ограничение, определившее архитектуру размещения**: этот же класс контента (правильное название документа) уже дважды приводил к откату функциональности (см. разделы про PMBOK ITTO и IDEF0-карточку выше) именно потому, что появлялся РЯДОМ с конкретной строкой ловушки занятия 2 — студент просто копировал ответ. 1. **Справочник в занятии 2** — новая панель сразу после обеих панелей счётчиков-ловушек (`renderCurrentLesson`, case 2, после строки со счётчиками квалификации, перед «Комплектующие проекта»). 2. **Приложение №5 к Договору** (case 4, п.13) — та же логика: до фиксации обеих ловушек — пометка-заглушка, после — полная таблица тем же контентом. Существующие Приложения №1-4 не тронуты.
3. **Раздел 11 итогового DOCX-отчёта** (`downloadFinalPracticeReport()`, после раздела 10 «Рефлексия», перед сборкой `documentXml`) — печатается БЕЗУСЛОВНО (отчёт формируется в конце практикума, гонка условий уже неактуальна), но с честной пометкой в тексте, если на момент печати ловушки так и не были зафиксированы студентом.

По прямой просьбе преподавателя («сделай так чтобы 2 кнопки давали такое действие = переход к следующему проекту»), после того как студент на занятии 9 нажал только кнопку «Итоговый отчёт (DOCX)» в шапке и не понял, почему рулетка следующего портфеля не открылась — это две независимые функции (`downloadFinalPracticeReport()` просто печатает документ, `submitProjectReport()` меняет статус и открывает рулетку), и до этой правки они никак не были связаны.

Направление связи выбрано намеренно одностороннее (`submitProjectReport` → `downloadFinalPracticeReport`, а не наоборот и не взаимно), чтобы не получить цикл вызовов.

Четыре сценария: (1) клик по кнопке DOCX на занятии 3 — 1 вызов печати, статус проекта НЕ меняется; (2) клик по кнопке DOCX на занятии 9 (реальный режим) — печать + статус «done» + открыта рулетка нужного портфеля; (3) прямой клик по «Сдать отчётность» на занятии 9 для проекта №2 — печать + статус «done» + `rouletteTargetChest` переключился на портфель III; (4) клик по кнопке DOCX на занятии 9 в тестовом режиме (`currentProjectIndex=-1`) — только печать, без попытки перехода и без циклов. Плюс полный регресс всех 20 типов × 9 занятий через `renderCurrentLesson()` — 0 исключений, 0 `window.onerror`.

**Правка того же дня (по жалобе «нет перехода — ничего не происходит»)**: `await downloadFinalPracticeReport()` внутри `submitProjectReport()` изначально ничем не был защищён. Сама `downloadFinalPracticeReport()` ловит ошибки СВОИМ try/catch, но код ДО этого try (запрос ФИО/группы через `prompt()`, работа с DOM-кнопкой) не защищён — если там что-то бросает исключение в реальном браузере (где canvas/JSZip реально выполняются и могут дать сбой не так, как в тестовой песочнице, где они просто не загружены), весь `await` прерывается БЕЗ единого alert'а, и студент видит полную тишину вместо перехода к рулетке — печать документа была БЛОКИРУЮЩИМ условием для перехода, хотя не должна была. Исправлено: `await downloadFinalPracticeReport()` обёрнут в собственный try/catch внутри `submitProjectReport()` — если печать не удалась, показывается отдельное предупреждение («⚠️ Не удалось сформировать DOCX-отчёт... но переход всё равно выполняется»), и переход к следующему проекту выполняется ВСЕГДА, независимо от успеха печати. Проверено (jsdom, `downloadFinalPracticeReport` подменена на функцию, которая гарантированно бросает исключение): статус проекта всё равно становится `done`, рулетка следующего портфеля всё равно открывается, `window.onerror` = 0.

## КРИТИЧЕСКИЙ БАГ: вкладки занятий 3-9 никогда не разблокировались — практикум был непроходим целиком — 07.08.2026

По прямому вопросу преподавателя («что у тебя ВШИТО как триггер ПЕРЕХОДА к следующему проекту из второго или третьего портфеля?») при разборе логики перехода между портфелями обнаружен несравнимо более серьёзный баг ниже уровнем: реальный студент не мог продвинуться дальше ЗАНЯТИЯ 2 ни по одному из 20 типов проекта — то есть вопрос о переходе между портфелями был преждевременным, до него дело физически не доходило.

**Причина.** Класс `.locked` снимался с вкладок `#lessonTabs` только для занятия 1 и 2 (`goToProject()`, вызывается после Старта 0). Ни для занятий 3, 4, 5, 6, 7, 9 не было ВООБЩЕ никакого кода, который снимал бы с них `.locked` в обычном игровом потоке — исчерпывающий grep по всему файлу это подтвердил. Кнопка «Перейди к следующему этапу практикума →» вызывает `goNextGated()` → карточка теории (2 клика) → тест на компетенции → «Продолжить» → в итоге всё сводится к `nextLesson()`, а та перед переходом проверяла `nextTab.classList.contains('locked')` и, поскольку это условие было истинным всегда (кроме перехода 1→2), просто показывала alert «Занятие N пока заблокировано» и отказывала — НАВСЕГДА, ни один тест/секретный код/повторная попытка это не обходили, т.к. блокировка была на уровне вкладки, а не теста.

Функция `goToAuditStage()` (задумывалась как прыжок сразу к занятию 8) существовала в коде, но не была подключена НИ К ОДНОЙ кнопке — мёртвый код, не имеющий значения даже если бы был вызван, т.к. общий механизм всё равно был сломан. Удалена.

**Почему это не было замечено раньше, несмотря на десятки сессий «полного прохождения практикума» для путеводителя/скриншотов**: каждый такой прогон в истории проекта либо использовал `skipWizard()` + ручную установку `state`/`currentLesson` через консоль/jsdom (обходит вкладки полностью), либо кнопку «Загрузить ранее созданный проект — пропустить опрос и рулетку» (`loadSavedProject`, тестовый профиль «Тестовый Клиент»), которая одним вызовом снимает `.locked` со ВСЕХ вкладок разом — то есть НИ ОДНА из прошлых проверок не тестировала по-настоящему последовательный клик через реальную кнопочную цепочку `goNextGated()→nextLesson()`. Баг обнаружен только когда впервые понадобилось объяснить механику ПЕРЕХОДА, а не просто снять цифры с уже готового состояния.

**Исправление** (`nextLesson()`, index.html): т.к. эта функция вызывается ИСКЛЮЧИТЕЛЬНО как `proceedFn` из цепочки `goNextGated()→openGateModal()→proceedAfterGate()→(тест)→«Продолжить»`, к моменту её вызова гейт (теория + тест) уже пройден — значит, разблокировка следующей вкладки прямо здесь не является обходом защиты, а лишь фиксирует уже состоявшийся факт. Заменена строка с `alert(...); return;` на снятие `.locked` со следующей вкладки перед `gotoLesson()`. Разблокировка сделана ИМЕННО в момент перехода (а не разом для всех 9 вкладок при старте проекта), чтобы студент не мог кликнуть по вкладке далеко впереди в обход теории/теста — обработчик клика по вкладке (`#lessonTabs`) идёт в обход `goNextGated()` и по-прежнему проверяет `.locked` сам.

**Проверка** (jsdom, эмуляция РЕАЛЬНОЙ кнопочной цепочки — не прямой вызов `nextLesson()`, а полный путь `goNextGated()`→2 клика по гейту→`gradeCompetencyTest()`(тестовый шорткат)→клик «Продолжить»): до исправления — `currentLesson` замирал на 2, alert «Занятие 3 пока заблокировано». После исправления — все 20 типов проекта проходят полный путь 1→9 без единого блокирующего alert и без единой JS-ошибки (`window.onerror` = 0).
